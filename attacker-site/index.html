🔬 Análise Técnica do Ataque

1
Vítima está logada no SafeBank (localhost:3000)
O browser armazena o cookie de sessão definido pelo banco:
Set-Cookie: session_id=abc123; Path=/; HttpOnly; SameSite=None # SameSite=None → cookie enviado em requisições de QUALQUER origem
2
Vítima acessa esta página (localhost:4000)
O script executa automaticamente — sem clique, sem confirmação.
3
Formulário oculto é submetido para o banco
O formulário aponta para outro domínio. O browser envia o cookie junto:
<form action="http://localhost:3000/api/transfer" method="POST" target="csrf-frame"> <input name="to" value="bob" /> <input name="amount" value="5000" /> </form> # Browser anexa automaticamente: Cookie: session_id=abc123
4
Servidor processa a requisição como legítima
O endpoint vulnerável só verifica o cookie — sem token CSRF:
// ❌ Sem verificação de CSRF token // ❌ Sem validação de Origin/Referer const sessionId = request.cookies.get('session_id')?.value // Sessão válida → transferência executada
5
Como corrigir
// ✅ Gerar token CSRF único por sessão const csrfToken = crypto.randomUUID() session.csrfToken = csrfToken // ✅ Incluir no formulário (campo oculto) <input type="hidden" name="csrfToken" value="..." /> // ✅ Validar no servidor if (body.csrfToken !== session.csrfToken) return 403 // ✅ Cookie com SameSite=Strict Set-Cookie: session_id=...; SameSite=Strict

O atacante não tem acesso ao token (Same-Origin Policy impede leitura cross-origin) → o formulário forjado não consegue incluir o token correto → servidor rejeita.
